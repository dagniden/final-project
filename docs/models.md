# Модели проекта

## 1. User

Кастомная модель пользователя на основе `AbstractUser`.

### Основные поля

- `username`
- `email`
- `password`
- `first_name`
- `last_name`
- `is_active`
- `is_staff`
- `date_joined`

### Примечание

- Проект новый, поэтому кастомного пользователя лучше заложить сразу.
- При необходимости позже можно будет добавить, например, `middle_name`, `phone_number`, `role`.

---

## 2. Author

Модель автора книги.

### Поля

- `id`
- `first_name`
- `last_name`
- `middle_name` — опционально
- `birth_date` — опционально
- `death_date` — опционально
- `biography` — опционально

### Связи

- один `Author` может быть связан со многими `Book`
- связь с `Book` — `ManyToMany`, так как у книги может быть несколько авторов

---

## 3. Genre

Модель жанра.

### Поля

- `id`
- `name` — уникальное название жанра
- `slug` — опционально, удобно для URL и фильтрации
- `description` — опционально

### Связи

- один `Genre` может быть связан со многими `Book`
- связь с `Book` — `ManyToMany`

---

## 4. Book

Карточка книги как произведения / издания, без учета конкретного физического экземпляра.

### Поля

- `id`
- `title`
- `description` — опционально
- `publication_year`
- `isbn` — опционально, желательно уникальный при наличии
- `publisher` — опционально
- `language` — опционально
- `created_at`
- `updated_at`

### Связи

- `authors` -> `Author` (`ManyToManyField`)
- `genres` -> `Genre` (`ManyToManyField`)
- один `Book` может иметь много `BookCopy`

### Примечание

- `Book` хранит только общую информацию о книге.
- Физические экземпляры хранятся отдельно в `BookCopy`.

---

## 5. BookCopy

Конкретный физический экземпляр книги.

### Поля

- `id`
- `book` — ссылка на `Book`
- `inventory_number` — уникальный инвентарный номер
- `status` — статус экземпляра
- `condition` — опционально, состояние экземпляра
- `location` — опционально, место хранения
- `created_at`
- `updated_at`

### Возможные значения `status`

- `available` — доступна для выдачи
- `loaned` — выдана пользователю
- `lost` — утеряна
- `damaged` — повреждена
- `written_off` — списана

### Связи

- `book` -> `Book` (`ForeignKey`)
- один `BookCopy` может иметь много записей в `Loan` во времени

### Примечание

- Именно `BookCopy` участвует в выдаче, а не `Book`.
- По `BookCopy` можно понять, где находится конкретный экземпляр и какова его судьба.

---

## 6. Loan

Факт выдачи конкретного экземпляра книги пользователю.

### Поля

- `id`
- `user` — ссылка на `User`
- `book_copy` — ссылка на `BookCopy`
- `issued_at` — дата и время выдачи
- `due_date` — ожидаемая дата возврата
- `returned_at` — дата и время возврата, `null` если книга еще не возвращена
- `created_at`
- `updated_at`

### Связи

- `user` -> `User` (`ForeignKey`)
- `book_copy` -> `BookCopy` (`ForeignKey`)

### Бизнес-смысл

- хранит историю выдач
- позволяет понять, кто сейчас держит экземпляр
- позволяет отслеживать возвраты и просрочки

### Базовые правила

- выдать можно только `BookCopy` со статусом `available`
- при выдаче статус `BookCopy` меняется на `loaned`
- при возврате заполняется `returned_at`, а статус `BookCopy` меняется на `available`
- у одного `BookCopy` не должно быть более одной активной выдачи одновременно

---

## Итоговая схема связей

- `User` 1 -> N `Loan`
- `Author` M <-> N `Book`
- `Genre` M <-> N `Book`
- `Book` 1 -> N `BookCopy`
- `BookCopy` 1 -> N `Loan`

---

## Почему выбрана такая схема

- `Book` хранит описание книги, а не складской остаток
- `BookCopy` решает задачу учета физических экземпляров
- `Loan` хранит историю движения экземпляров между библиотекой и пользователями
- схема хорошо подходит под библиотечный и складской учет, а также нормально расширяется в будущем
